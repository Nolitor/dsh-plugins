## 1. 감사 범위와 방법

**Scope.** `@nolit/dsh-tokeneconomizer` (측정 시점 `0.0.1-rc.3`) — 세 축을 각각 실측했다.

1. **축 1 — 스키마 적합성**: 플러그인이 인용하는 DSH 확장점이 설치본 `@deepseek-ai/dsh@0.2.2-rc.3`의 원문과
   verbatim으로 일치하는지, 그리고 DSH가 실제로 무엇을 보장하는지(계약 주석 포함)를 대조했다.
2. **축 2 — 실제 토큰 절감**: 이 플러그인이 **실제로** 토큰을 절감했는지, 어느 정도인지. 계층 재작성(tiering),
   중복 제거(dedup), 도구 마스크(toolprune) 세 lever 각각에 대해 실측했다.
3. **축 3 — 설정 탭**: Settings 좌측 목록에 "토큰절약기" 항목이 등록·렌더되는지.

**Read-only.** 이 감사는 **읽기 전용으로만 수행했다.** 무엇도 고치지 않았다.

**주의(플러그인의 게이트에 대한 리스크).** DSH는 `origin`을 다음과 같이 규정한다.

> "Coarse product classification for a session created as a subagent child. This is **presentation
> metadata, not proof** that the child is continuable." — `dsh-session/lib/types/types.d.ts:82-86`

플러그인은 `lib/index.js:488`에서 `header.origin === 'subagent'`를 **100% 게이트**로 쓴다
(§4.3 참조). 즉 DSH가 "증명 아님"이라고 경고한 필드에 동작을 전적으로 묶고 있다. 현재는 실측상
판별자가 유효하므로 문제가 발현되지 않았지만, 계약이 보장하지 않는 필드에 의존한다는 사실은
문서에 남아 있어야 한다.

> **[후속]** 감사 시점 이후 같은 날 이 게이트는 **엔진 경로에만** 적용되도록 좁혀졌다
> (**§10**). `origin` 에 의존한다는 리스크 자체는 남는다 — 100% 게이트에서 "엔진 경로 게이트"로
> 줄었을 뿐이다.

### 3.2 Session HeaderLine 실제 스키마

문서에 없던 필드가 세 개 있다.

```ts
{ type:'session', version, id, createdAt, cwd?, isSeeded,
  delegationDepth, origin?:'subagent', parentSession?, agentPreset? }
```

- 근거: `docs/persistence-catalog.md:3722-3739` (HeaderLine 표), `dsh-session/lib/types/types.d.ts:70-99`

| 필드 | 존재 | DSH의 계약 주석 | 플러그인의 사용 |
|---|---|---|---|
| `origin` | 선택 (`'subagent'`) | "presentation metadata, **not proof** that the child is continuable" | **100% 게이트** (`lib/index.js:488`) — 감사 시점 표기. **[후속]** 이제 **엔진 경로 게이트**로 좁혀짐 (§10) |
| `parentSession` | 선택 | "Presence alone does **not** classify a Session as a subagent; use `origin`" | **미사용** |
| `delegationDepth` | 필수 (0 = top-level) | "absent (zero) for a top-level session, parent depth + 1 for a subagent child" | **미사용** |

실측 로그 확인:

- subagent 세션 = `origin:'subagent', delegationDepth:1, parentSession:'session-…', agentPreset:'cordis'`
- 메인 세션 = `origin` 부재, `delegationDepth:0, agentPreset:'standard'`, `parentSession` 부재

`delegationDepth`는 재귀 예산 때문에 **영속**되는 필드인데, 플러그인은 서브에이전트를 `origin` 하나로만
구분한다. 두 필드를 함께 보면 "하네스 배심원"이 아니라 "플러그인 에이전트"를 정확히 판별할 수 있었을 것이다.

### 3.3 프로젝트 식별 — 이중 체계

**두 개의 서로 다른 키 체계가 공존하며, 어떤 문서에도 그 관계가 적혀 있지 않다.**

| 체계 | 주체 | 키 규칙 | 실측 |
|---|---|---|---|
| **프로젝트** | DSH | cwd 의 슬러그화 경로 | `--home-minami-Workspace-projects-dsh-workspace-dsh-plugins--` |
| **저장소** | TokenEconomizer 엔진 | origin remote → realpath → dir (3단계 폴백) | `lib/repokey.js` (`BY_REMOTE`/`BY_PATH`/`BY_DIR`) |

- DSH 세션 저장 위치: `~/.dsh/sessions/<project>/<session-id>/session.v4.jsonl.zstd`
- 저장소 루트 아래 프로젝트 디렉터리 **9개**, dsh-plugins 프로젝트 아래 **279** 세션 디렉터리 (측정 시점)
- `lib/repokey.js`의 헤더 주석은 이 규칙을 정확히 기술한다: "`repos/<slug>-<sha1(canon)[:10]>/<host>`, where
  `canon` is the normalized `origin` remote when the checkout has one, else the real path of the
  checkout's *main* clone … else the directory itself"

**왜 이중 체계가 문제인가.** 두 키는 **같은 차원을 다른 이름으로** 부른다. DSH의 "project"는 *디렉터리*이고
엔진의 "repo"는 *VCS 체크아웃*이다. 워크스페이스에 git 저장소가 아닌 디렉터리가 있거나, 같은 저장소의
worktree가 여러 개면 두 키가 갈라진다. `lib/repokey.js`는 "a wrong key misattributes every fold"
(REFACTORING.md §4)라고 스스로 경고한다. 이 관계가 문서화되지 않은 것은 **문서 공백**이다(§7).

### 4.2 측정 방법론 교정 기록 — 이 감사의 핵심 교훈

세 단계에 걸쳐 집계 방법이 바뀌었고, **각 단계는 다른 방향으로 틀렸다.**

| 단계 | 집계 방법 | 나온 수치 | 오차 | 왜 틀렸는가 |
|---|---|---|---|---|
| 1차 (구) | 마커 문자열 포함 여부 | **235** | **-88.6%** (과소) | 마커 문자열은 사용자의 grep/bash 출력이 그대로 **인용**된다. 235건 중 62건은 재작성 기록이 없는 **에코**였다. |
| 2차 (중간) | `surfaceOp.op === 'replace'` 전부 | **2,052** | **+9.6%** (과대) | 하네스의 `@deepseek-ai/dsh-compaction-tool-result-pruner`가 **플러그인과 완전히 동일한** `surfaceOp: {op:'replace', startSeq, endSeq}` + `sourceEventSeqs` 형태를 쓴다. 표면상 구분 불가. |
| 3차 (정) | `surfaceOp` + **본문 attribution** | **1,873** | 정확 | 본문 접두로만 구분 가능 |

**왜 이 교정이 중요했나.**

1. **1차(마커)는 과소보고였다.** 실적이 235로 보였고, 마커는 프로바이더 프롬프트 캐시(98.73%)에 비하면
  잡음 수준이라 "이 플러그인은 거의 아무것도 못 한다"는 결론에 도달하기 쉬웠다. 실제는 4.3% 구간의
   구조적 재작성이 있었다. **과소보고는 플러그인을 없애도 되는 것처럼 보이게 한다.**
2. **2차(surfaceOp 총계)는 과대보고였다.** 2,052 = 1,873 + 179. 하네스 프루너의 몫을 이 플러그인의
   실적으로 세면 **9.6% 부풀려진다**. **과대보고는 플러그인의 가치를 지어낸다.**
3. **3차(attribution)만이 정확하다.** 그리고 그 정확성은 **두 개의 독립 구현이 같은 값에 도달**했다는
   사실로 교차 검증되었다.

**Attribution의 방법과 한계 (반드시 함께 인용).**

- 방법: 재작성 본문의 접두로 판정한다.
  - warm: `[tokeneconomizer] warm tier: …` (`lib/tiering.js:148`)
  - cold: `[tokeneconomizer] cold tier: …` (`lib/tiering.js:164`)
  - harness: 본문에 `[... tool result middle pruned ...]` 포함 (`PRUNE_MARKER`, harness `lib/index.js:8`)
- **한계**: 미래에 하네스가 마커를 바꾸거나 플러그인이 접두를 다르게 쓰면 그 건은 `unattributed`로 빠진다.
  현재 `unattributed`는 **0건**이므로 지금은 누락이 없다. 그러나 **접두 기반 attribution은 계약이 아니라
  관례이며**, 양쪽이 바뀌면 조용히 0건이 된다.
- **경계 사례 1건 실측 확인**: `session-f8c40e19-…` seq 607 — 본문이 `[tokeneconomizer] warm tier:`로
  시작하면서 동시에 하네스 마커 문자열을 **포함**한다. 이유는 이 세션이 하네스 프루너의 소스 코드를
  읽어온 도구 출력이었기 때문이다(플러그인이 warm tier로 압축했다). 판정 로직은 접두를 먼저 확인하므로
  warm으로 정확히 분류된다. 다만 이것은 "접두 우선" 규칙이 실제로 필요했다는 증거다.
- **직접 재계산으로 확인**: `tool/result` + `surfaceOp.replace` 2,052건을 본문으로 직접 분류한 결과
  harness 180 / warm 1,828 / cold 44 / other 0 / unattributed 0 (합 2,052) — 위 표와 1건 차이는 위
  경계 사례의 classification 순서 때문이다. `compaction/prune` → `tool/result` replace 쌍으로 페어링하면
  harness 180 / warm 1,828 / cold 44 / sum 2,052 로 **정확히 일치**한다.

**추가 확인 — `compaction/prune` 이벤트.** corpus 전체에 `compaction/prune`가 2,052건 있으며,
**2,052건 전부**가 바로 다음에 `surfaceOp.replace`인 `tool/result`를 동반한다(플러그인 `lib/index.js:800-806`,
하네스 `lib/index.js:159-177` 모두 동일 패턴). 즉 2,052는 "재작성"과 1:1 대응하는 shadow-price 기록이고,
이벤트 자체는 절감량이 아니라 **기록**이다.

### 10.1 감사에서 지적한 결함은 수정됐다

### 10.2 두 경로의 분리

`agent/created` 뒤에는 **성격이 다른 두 경로**가 있다.

| 경로 | 포함 | 서브에이전트 | 이유 |
|---|---|---|---|
| **엔진 경로** | `SessionStart` / `UserPromptSubmit` / `PostToolUse` / `Stop` / `SessionEnd` 훅, Python 엔진, 세션 export→fold, ledger | **루트 전용** | 위임된 자식은 부모 작업에 합산 fold 된다. 자식이 자기 envelope 을 가지면 턴이 이중 계상되고, loop guard 가 아무도 안 도는 턴 스케일을 학습한다. |

### 10.4 라이브 미적용 — `applied pending restart`

**이 수정은 아직 실행 중인 프로세스에 반영되지 않았다.**

| 항목 | 시각 |
|---|---|
| `dsh-web` 서비스 기동 | **2026-11-14 09:37:14 KST** (`systemctl --user show dsh-web.service -p ExecMainStartTimestamp`) |
| `lib/index.js` 수정 | **2026-11-14 21:24:15 KST** (파일 mtime) |

소유자가 다른 작업을 진행 중이라 **재시작하지 않았다.** 따라서 상태는 **`applied pending
restart`** 다: 디스크에는 반영됐고, 소유 프로세스가 아직 그 상태를 읽지 않았다. 재시작 전까지
